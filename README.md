# CityLights / MOSAIC map generator

Original-city maps for Spring/Recoil, plus an **experimental map-contained startup** for unchanged Skylobby. The city is not mirrored. A deployment search finds two opposing starts on its movement graph; the startup preview rotates the view to show that axis without rotating the geography.

## Shared roads and addresses

Version 0.3.0 connects **generated by map** cities to MOSAIC's **generated by game** road/address service. Both execute the same pure Lua resolver. Map generation exports clipped OSM highway polylines to `mosaic/roads.lua`, retains street names and building `addr:street` / `addr:housenumber` tags, and includes structured plot addresses in `mosaic/placements.lua`. Connected same-name ways share a street ID; disconnected same-name streets remain distinct.

Generated house numbers follow stable world-plot ordering with odd/even street sides and skip imported numbers. Addresses survive repeated tooltip registration and destroyed-house rebuilding. The map's initial address plan is authoritative; the game handles the house lifecycle. Neither path's address resolver consumes RNG or uses unit creation IDs. The game-generated path infers lanes from its existing city grid. A new plot added after startup receives a coordinate suffix to preserve existing numbers.

The packaged **City roads** widget draws terrain-following strips at 50% opacity and decluttered names. It uses the public network published by the synced game, so both generation paths use the same renderer. This is a visual overlay; it does not modify pathfinding, terrain or house rotation. Road widths are estimates by OSM highway class; game roads use configured alley widths. Unicode names are retained. Road geometry is limited to 4096 pieces and 65536 points.

Packaging now requires the matching MOSAIC **City roads and addresses** update. An old street-counter game is rejected explicitly. Use the game branch/PR accompanying this generator update, or the merged game revision when available, and rebuild the archive for that exact checkout. Engine rendering and the existing multiplayer reload path remain unvalidated here.

## Distributed startup map

Build one SDZ and distribute it like an ordinary Spring map. Players select that map and the matching MOSAIC game in Skylobby. No lobby changes or player-side Python installation are involved.

The packaged Lua implements this flow:

1. Open an in-engine world selector. The room controller (lowest non-spectator player ID) clicks a location, chooses an extent, and presses Enter.
2. That client fetches one OpenStreetMap snapshot through Overpass. LuaGaia broadcasts the same frozen snapshot and settings to everyone; clients do not independently fetch changing city data.
3. Each client generates native SMF/SMT terrain and map-contained MOSAIC overlays into its own `maps/CityLights_<digest>.sdd` under the engine write directory. The folder name is identical across clients; the physical folder is local to each machine.
4. Each client verifies its files. The coordinator requires matching SHA-512 file hashes and a second readiness barrier from every room participant, including spectators.
5. The prototype calls `Spring.Reload` with a locally rewritten Skylobby `script.txt`. Host/client role, player identity, password and connection endpoint stay local. The host starts first; clients follow. The generated map uses the audited starts.

All generation code, profiles, world outlines, native exporter and checked game overlays ship inside the distributed map. MOSAIC's checkout is read only during packaging. The game overlays are written into the generated map, so the distributed-startup workflow does not install an adapter into the game.

### Package and install

An experimental prebuilt archive is in [artifacts/MOSAIC_CityLights_World-experimental.sdz](artifacts/MOSAIC_CityLights_World-experimental.sdz), with checksums and limits in [startup-map.json](artifacts/startup-map.json). It requires the exact MOSAIC sources recorded inside the archive; build your own when using a different game revision.

Packaging requires Python 3.11+, and an unpacked MOSAIC checkout matching the game you will run:

```sh
python -m pip install -e '.[test]'
python -m mosaic_mapgen package-startup-map --game-dir /path/to/MOSAIC --out build/startup
```

Copy **one** of these into the Spring/Recoil write directory's `maps/`:

- `build/startup/MOSAIC_CityLights_World.sdz` for distribution.
- `build/startup/CityLightsWorld.sdd` for development; copy the entire directory.

Do not install both simultaneously. Refresh Skylobby's map inventory, choose the printed `MOSAIC CityLights World <identity>` map, select the matching MOSAIC game, and create exactly two opposing allyteams. Start the room normally. In the map UI: click Earth to select, mouse wheel changes radius (100–3000 metres), L cycles landscape, Enter fetches and generates, Escape retains the engine quit menu. Standard map options provide the seed and initial coordinates without changing Skylobby.

The selector accepts coordinates across Earth. Country names are resolved from OSM areas; unprofiled countries use international architecture. A selectable location is not a guarantee of a playable map: empty, ocean, incomplete or unusably disconnected districts fail explicitly. Landscape is chosen explicitly, not inferred climate or DEM data. Natural Earth outlines are bundled; `--world-geojson` can replace them with another appropriately licensed outline dataset.

### Runtime boundary — not yet engine validated

This is a tested Lua/package prototype, **not a demonstrated multiplayer integration**. No Recoil engine was available for loading or two-client handoff tests. Treat the reload path as experimental until the acceptance checks below succeed on your engine and Skylobby versions.

Current constraints:

- Player-hosted rooms only. Headless autohosts and relay hosts have no LuaUI fetcher and are unsupported.
- Exactly two opposing allyteams; an 8192-unit map container. Starts are fixed by the graph search.
- Requires map LuaGaia, MOSAIC map-widget loading, LuaUI LuaSocket, write-directory file access, SHA-512 `VFS.CalculateHash`, and internal `Spring.Reload`. Older Spring/BAR builds may lack the required behavior.
- The packager checks MOSAIC loading anchors. Each client checks base-game source hashes before generation. Rebuild the map when these game files change.
- The fetcher currently uses HTTP port 80 on `overpass-api.de`, with bounded cooperative reads, a 120-second timeout and an 8 MiB snapshot cap. TLS, redirects and configurable providers are not implemented. Live fetch could not be validated from this workspace: requests were rejected with HTTP 406. Engine socket restrictions or provider policy may block it.
- OSM tagged nodes and ways are imported; relation multipolygons and complete coastlines are not resolved. GeoJSON currently uses the first outer polygon ring/component. Roads/water/green areas are rasterized; dense building lots are thinned, and explicit gameplay infill supplies missing sites. Terrain is flat land and water beds, not geographic elevation.
- A failed/disconnected participant blocks handoff. Automatic retry, late joins, replays and saved-game restoration across the bootstrap/reload boundary are not supported.
- Skylobby continues to advertise the bootstrap map. Whether reconnecting clients and the lobby remain coherent through internal reload is a required engine test, not established by protocol unit tests.

## Original-city graph balance

The full source district is projected uniformly into the map with aspect preserved. Roads are cheaper movement edges; water and conservative building footprints block the four-neighbor 64-unit graph. The planner searches opposing deployments around three inset perimeters and compares weighted objective access, `sum(value / (1 + distance / 20))` for each side. Candidate order resolves ties deterministically.

The default acceptance threshold is 8% relative opportunity imbalance. Both starts must connect and reach every objective. Failure reports the best imbalance rather than inventing equal opportunities. Camera rotation only changes the preview; searching starts changes gameplay access. The audit does not simulate engine pathfinding, combat cover, asymmetric factions, objective income differences or win rates. Exact equality is not promised.

Cache identity includes generator version, packaged adapter identity, resolved geographic metadata, settings and source features. In-engine requests additionally include the exact snapshot hash. Clients agree on actual output-file hashes before attempting reload; a damaged existing cache is rejected instead of overwritten.

## Offline build and tests

```sh
python -m pip install -e '.[test]'
python -m unittest discover -s tests -v
python -m mosaic_mapgen build --city examples/berlin-fixture.geojson --config examples/berlin.json --out build/demo
```

The included Berlin example is an **invented CC0 test fixture**. Outputs are `MOSAIC_city.sdz`, unpacked `map/`, `preview.png`, `balance.json`, `manifest.json`, and `resolved-config.json`. The default build executes the same Lua city planner used by the startup map. `--legacy-mirror` retains the superseded mirrored Python generator for comparison.

Google Maps URLs can select an offline fetch location; no Google imagery or map data is imported:

```sh
python -m mosaic_mapgen fetch --google-view 'https://www.google.com/maps/@52.52,13.405,15z' --radius-m 800 --out berlin.geojson
```

Use explicit `city`, `latitude`, `country_code`, `landscape`, and `seed` in the configuration. Country profiles cover 36 ISO codes; custom offline country profiles require `country`, `region`, and `culture`. Cultures are `western`, `arabic`, `asian`, or `international`; landscapes are `temperate`, `arid`, `tropical`, `alpine`, or `mediterranean`. Existing MOSAIC UnitDefs supply houses and objectives.

Standalone offline maps need the game adapter because they do not bundle the patched game sources. On a dedicated checkout, preview then apply:

```sh
python -m mosaic_mapgen install-game-adapter --game-dir /path/to/MOSAIC
python -m mosaic_mapgen install-game-adapter --game-dir /path/to/MOSAIC --apply
```

This legacy installer backs up originals and refuses unknown function anchors. It is not needed for the distributed-startup package.

Tests execute Lua 5.1 and cover strict data-only JSON, local credential preservation, malformed/different snapshots, every-client readiness barriers, unmirrored geometry, deployment connectivity, preview rotation, SMF/SMT offsets, independently decoded BC1, reproducible archives, game-source compatibility and adapter behavior. To check actual MOSAIC sources as well:

```sh
MOSAIC_SOURCE=/path/to/MOSAIC python -m unittest discover -s tests -v
```

CI runs on Linux and Windows and uploads the synthetic offline example. It does not claim an engine test or publish a release.

## Engine acceptance checks

Before distributing this as playable:

1. Load the startup map with unchanged Skylobby and the exact packaged MOSAIC revision. Check map LuaGaia, the staging gadget override, world rendering and quit controls.
2. Use two machines plus a spectator. Fetch a real district; confirm identical snapshot hashes, generated folder names and file hashes, and visible original-city graph/imbalance.
3. Let reload complete. Check host binding, client reconnection, archive discovery/checksums, room state and spectator reconnect. A successful local generation is not a successful handoff.
4. Verify fixed starts, all game units and objective capture/destruction/restoration, culture/weather metadata and movement through the city. Measure performance on representative hardware.
5. Exercise provider errors, socket restrictions, mismatched MOSAIC versions, altered caches and participant disconnection; ensure errors remain explicit and gameplay never starts on different maps.
